Don't let a model pick its own score

Ask a model yes-or-no questions, compute the score in code, and test the judge on cases you already know.

A common pattern: hand a model a piece of work and ask for a score out of ten. Work scoring above seven moves on. It looks like judgement. In practice the scores bunch around one comfortable number, and the threshold ends up deciding by noise.

What works better

Ask concrete questions with yes or no answers. Not "how strong is this idea?" but "does the text name who pays?", "is there an existing product that does this?", "does it need a licence to operate?". Small models are far steadier on these.

Compute the score in code. Each answer carries a weight you chose and can read. The model reports facts; arithmetic you can inspect turns them into a decision. When the outcome is wrong you can see which answer was wrong, instead of staring at a 6.5.

Test the judge before trusting it. Keep a set of cases whose right answer you already know, good and bad. Run the judge over them whenever its prompt or model changes. A judge that passes everything is not strict, and a judge that fails everything is not careful. Until you have checked, a pass rate is just a number.

Healthy means useful

The same trap exists one level up. A system that reports "running" every minute can be producing nothing. The health check worth having counts useful output per hour and asks whether each learning loop actually fired.

Where a model's opinion still fits

As a second look that can only add warnings. The gate that decides whether this site may publish works that way: fixed checks decide, and a local model may raise a flag for a reader to look at. It cannot wave anything through.
